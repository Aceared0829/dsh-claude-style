# D66. 三层测试、单一入口与闸门的发起时机

- **状态**：已实施
- **分组**：分发与流程
- **关联**：D40、D44、D46、D47；取代 D45

## 决定

- 所有测试由一个入口发起：`scripts/verify.mjs`（`npm run verify`）依次跑云端快档那批检查（lint、特性清单、决策索引、变更记录、AGENTS 表）、构建、单元测试、冒烟与端到端通道。同一工作树同时只允许一次运行（锁在 `.debug/verify.lock/`），结论按「树内容的散列 + 本次闸门集合」记进 `.debug/verify-cache/`，同一棵树上的再次请求直接读这份结论并注明是哪一次跑出来的，`--force` 才重跑；等待中的请求在锁放开后先查一次结论，因此并行会话排队而不是各起一套浏览器。
- 一次运行的工作树锁由 `scripts/shared/verify-lock.cjs` 提供：`npm run build`、冒烟、端到端通道与在线探针也取它，运行自己启动的闸门与 `npm run dev` 的重建继承已持有的锁；持有者长时间不放手时按它写下的开始时刻接管。运行期间 `npm run dev` 的重建换掉了构建产物时，这次运行不写下结论。
- 闸门的发起时机：本机默认不起闸门，一次运行只属于推送之前那一段，取覆盖这次改动的最小集合，在后台发起；分支推送在云端跑快档，pull request、master 与手工触发再加上端到端通道与契约预警，要判断单独一次提交就把它推到一个分支上；完成的判定以推送后云端的结果为准。
- 一次请求的范围由它自己的参数决定：不带参数的请求就是推送前那一档，跑快档那批检查、构建、单元测试与冒烟的快档，端到端通道只由 `--e2e`、`--scenario` 与 `--full` 加进来；`--case` 与 `--feature` 走冒烟里点名的用例并连带动效用例，`--full` 走整份冒烟与端到端通道的默认表，起跑前打印一句「请确认你正处于发布流程。」，因为这一档就是云端的发布闸门。
- 结论只对它读过的那棵树成立：后台运行期间继续改动会让那次结论过期，要判断当前这棵树就用同一套参数再发起一次，命中已记录的结论即刻回答。
- 推送由 `npm run session -- finish` 发起（D68）：finish 先请求推送前那一档，失败拒绝推送。
- 发版时工作流先把这一版发成 `dev` 版本，快档那批检查、Windows 上的完整冒烟与端到端通道全部通过之后才把同一份产物转正；本机不发版，也不跑闸门（产物、标签与分支的做法见 D47）。
- 单元测试（Vitest，浏览器模式跑在本机 Chrome 上）覆盖纯逻辑：弹簧曲线、气泡形状采样、折行分段、吉祥物状态机、偏好解析、观察总线的分发顺序（D40）、滚动主人的仲裁与接管（D41）。毫秒级，改一行就能跑。构建生成的模块（D36）在测试里由配置按同一份数据写到 `.debug/vitest/`，模块在测试中读到的动效令牌与页面上的一致（D65）；生成模块里那些需要 bundle 的名字不提供，够不到的名字会在导入时报错。
- 契约测试见 D44：宿主选择器与入口逐条对着真实页面核对。
- 可运行的验证工具全部住在 `packages/testing/`，共用一套浏览器栈：`packages/testing/browser.cjs` 是唯一找本机 Chrome、开页面、注入启动脚本与关掉浏览器的地方，冒烟、端到端与在线探针都从它取页面，各自不再带一份启动方式。四条通道各是这里的入口：
  - 冒烟（`packages/testing/smoke.cjs` 与 `smoke/` 各部件）跑在仓库自己的替代宿主页面上，用例表来自各功能清单（D42），是发布前的完整闸门；每个页面新开一个上下文，页面之间不留缓存与存储。
  - 端到端通道（`packages/testing/e2e.cjs`）跑在装配好的真实宿主上，见下。
- 在线探针 `packages/testing/probe.cjs`、`probe-timing.cjs` 与 `shoot.cjs` 对着一个已经在跑的实例量真实时序，`--token` 与 `--url` 由命令行或环境变量给。
  - 契约探针 `packages/testing/contract-probe.cjs` 按 D44 的表逐条核对。
- 端到端测试（Playwright）跑在装配好的宿主上：
- `packages/testing/dsh-web.cjs` 起一个临时实例：`$DSH_HOME` 在 `.debug/` 下，本仓库以链接装进它的 web 配置，交出带令牌的地址；通道自己的补丁走 `--patch` 覆盖层。实例的标准输入是一条只由启动进程持有的管道，`packages/testing/lifeline.cjs` 经 `NODE_OPTIONS` 预加载进宿主，读到管道关闭就结束宿主，启动进程无论怎样结束都不会留下后台实例。
  - `packages/testing/mock-llm.cjs` 是脚本化的模型服务，按 Messages 协议回答宿主路由，脚本按请求顺序交付；只有模型是脚本化的，agent 循环、会话、客户端各层与渲染都是发行版宿主。
- 端到端通道按职责分成几份：`packages/testing/e2e.cjs` 是运行器（每个场景起一套实例、在轮次进行中逐帧采样、失败时写下现场），`scenarios.cjs` 是场景表，`lane.cjs` 放运行器与场景共用的页面标记与断言形状，`contract-probe.cjs` 放契约表的逐条核对；场景可以给宿主的命令行与浏览器各加参数，也能从 npm 装别的插件的固定版本，装在只属于它的临时目录里。默认的那次走表里除停放的两个统计场景之外的全部条目，名单由 `packages/contracts/src/timing.ts` 的表与停放名单算出，新加入表的场景因此默认进入通道。
- 每个场景各起一套实例、断言各自的东西：断言写在各场景自己的模块里（`packages/testing/*.cjs`），挂进 `packages/testing/scenarios.cjs` 的场景表，自带读取逻辑的场景自己逐帧采样；每个场景断言什么，写在它模块开头的说明与场景表的条目里。
  - 截图沿用写盘前的隐私替换与泄漏扫描（`scripts/shared/privacy.cjs`，与 `packages/testing/shoot.cjs` 共用），两套明暗各写一张到本次运行的输出目录供人查看；仓库不存比对基线，画面是否变样由用户看过再定。
- 持续集成的触发：分支推送与 pull request 都跑，标签推送只交给发布工作流；并发组按事件与提交划分，同一提交上的重复事件取消先前的那次，不同提交的运行各自跑完。
- 持续集成（`.github/workflows/ci.yml`）：构建检查、单元测试与完整冒烟在 Linux 上跑；完整冒烟另在 Windows 上跑一遍（读者的桌面端在那里读会话目录、盘符路径与文件时间）；端到端的行为场景与截图捕获在 Linux 上跑，宿主版本固定；`contract` 场景另对宿主最新的预发布版跑一遍，只作预警，不挡合并。每个任务都有时限，工作流用到的 Actions 由 Dependabot 每周提更新。
- `.debug/` 里有价值的探针已升级为有维护的工具：逐帧滚动记录并入 `scroll` 场景，发送过程录制并入 `send` 场景的逐帧采样，替身采样并入同一份采样；其余草稿在会话结束时删除。

## 理由

- 冒烟跑在替代宿主页面上，发现得了结构与标记的回归，发现不了真实宿主的时序问题；只靠人工运行的探针又把这类问题留给了下一次手工排查。
- 三条通道各自带一份浏览器启动细节时，找 Chrome、开页面、注入启动脚本与截图这几件事要在多处各写一遍，改一处漏一处；收进 `packages/testing/browser.cjs` 之后，新增一条验证只写它自己的断言。
- 并行会话共用一棵工作树，各自挑一条命令跑会把同一份构建与同一套浏览器重复启动一遍；结论按树内容复用之后，第二次请求不必再启动浏览器，拿到的判定是真实跑出来过的。本机跑一次完整矩阵以分钟计，开发期频繁发起把时间花在等待上，而同一棵树上重复的结论并不给出新的信息；完整矩阵在每次推送时已由持续集成跑过一遍。
- 绕过本地判定直接推送的账：云端红一次的修复路径是再改、再跑本地、再推、再等一轮云端，预期代价是一次完整的云端往返加一次重推，数量级高于推送前那一档的秒级成本。判定绑在推送动作上之后，这个取舍不再留给发起者的自觉。
- 云端与本地各回答一个问题：云端回答「这次推送在干净环境、双系统与完整走查下是否成立」，本地快档回答「已知的错误在推送之前拦下」；两者结论相同、延迟不同，用云端回答第二个问题买到的是同样的判定晚几分钟、外加一次多余的推送。云端不可替代的部分是没有本地等价物的判定：Windows 上的冒烟、端到端全量与宿主 alpha 契约预警。

## 代价

- 云端跑完整矩阵要装 DSH、pnpm 与 Chrome，端到端部分耗时以分钟计；本机不跑这套矩阵，改动的判断因此落在推送之后；快档在每次分支推送时都跑，机器时间随推送次数增长；发版也等这套矩阵整轮跑完才转正，标签推送到正式发布之间的时间因此变长。
- 各条通道共用一套浏览器接口，探针要用这套接口之外的能力时，先给共享的浏览器模块加接口。
- 结论按树内容复用，因此改动与闸门无关的文件（例如文档）也会让下一次请求重跑，`--force` 用来强制重跑一棵没有变化的树；排队意味着一次完整运行会挡住同一工作树上随后发起的请求，等待中的请求要么等到这次跑完，要么命中它刚写下的结论。
- 没有 Chrome/Edge 的机器上冒烟起不来，finish 的推送永远被闸门的失败拒绝：这类机器只编辑，推送交给有浏览器的机器。

## 重审条件

- 宿主提供官方的插件测试环境时改用宿主的。
