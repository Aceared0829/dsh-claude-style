# D69. 持续集成的构成与发起时机

- **状态**：已实施
- **分组**：分发与流程
- **关联**：D47、D66

## 决定

- 触发：推送到 master、pull request、合并队列与手工触发都跑这一份工作流，没有 pull request 的分支推送不跑，那条分支的工作由 pull request 或合并队列判定；标签推送只交给发布工作流。并发组按事件与提交划分，同一提交上的重复事件取消先前的那次，合并队列里的那次不取消，因为合并正等它的结论。
- 一个只读改动的任务（`scripts/ci-scope.mjs`）在其它任务之前定下这一轮的范围：只改了文档、语言包或工作流本身的推送把读页面的任务全部跳过，改动落在一个功能目录内时冒烟只走那个目录的用例，其余改动走完整冒烟。范围写成任务的输出，后面的任务据此决定跑不跑。
- 任务划分：不需要构建的检查一份，构建、单元测试与冒烟一份，完整冒烟在 Windows 上另一份，端到端的行为场景与截图捕获按矩阵分成四份，`contract` 场景对宿主最新预发布版单独一份且只作预警。读页面的任务只等检查那一份，不与构建那份互相等待；工作流用到的 Actions 由 Dependabot 每周提更新。
- 端到端通道的默认表由 `packages/testing/e2e.cjs --shard <序号>:<总数>` 切片：场景之间互不依赖，各份合起来正好覆盖整张表，每份按自己的编号上传失败现场。
- 构建的慢步骤（Deepy 的图与文本资源的压缩）按树内容的散列在运行之间取回（`scripts/shared/tree-hash.mjs`），缓存键按运行平台分开；`lib/` 的字节与没有缓存时相同。
- 分支规则只登记一个汇总任务（`scripts/ci-required.mjs`）：它读各任务交来的结果，失败或取消即失败，跳过的算通过，任务的增删改名都不必改分支规则。
- 每个任务与每个分钟级的步骤都写时限：任务的时限是兜底，步骤的时限让一次卡死的等待在几分钟内结束。

## 理由

- 一份工作流分档之后，改一处文档与改一个功能付的机器时间应当不同：前者只需要检查，后者需要真实页面。
- 端到端通道的场景彼此独立，串行走完整张表的耗时是各场景之和；分片之后这个耗时接近最长的一份。
- 分支规则按名字登记任务时，新增的任务不登记就永远不挡合并，而漏登记不会以失败的形式暴露。

## 代价

- 分片把失败现场分散到几份产物里，读日志要按分片编号找。
- 路径映射认不出的改动走完整冒烟，新增一类目录时这一步仍然慢。

## 重审条件

- 合并队列能在更短的时限内给出结论时，把分片数降下来。
