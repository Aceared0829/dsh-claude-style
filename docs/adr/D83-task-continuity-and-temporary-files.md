# D83. 工单用于延续任务，临时文件独立退役

- **取代**：D82

## 背景

小范围修改、只读检查和一次性试验通常能在当前会话完成。为这些工作填写目标、验收、测量去向和审核状态，会让记录的成本超过工作本身。临时脚本、截图和日志却会在任何规模的任务中产生，它们都需要明确的归属与删除时机。

需要跨会话恢复、多人交接或持续积累验收证据的工作，仍然需要把上下文留在一个地方。工单保存这份上下文，临时文件的生命周期另有自己的拥有者。

## 决定

- 范围明确、当前会话能够完成的小修改、只读检查和一次性试验直接进行。没有中间产物时不建立临时目录。
- 用户明确要求工单，或任务需要跨会话恢复、多人交接、持续积累验收证据时，由执行任务的代理自动建立或复用工单。修改行数、文件数量和是否产生临时文件都不单独触发建单。
- 一次性产物按会话或运行放进 `.debug/tmp/` 下的独立目录，记录所属进程与活动时间。正常结束的运行删除自己的目录，失败运行保留证据；异常遗留在保留期限过去且所属进程已经结束后回收。清理按整个运行目录进行，存活进程与目录链接受保护。
- 工单仍住在 `.debug/work/`，其 `refs/`、`shots/`、`tmp/` 保存随工单一起交接的资料。测量在进入 review 前写明去处：令牌、规范、注释、架构决策或不持久。关闭工单时删除整个目录。
- 构建、测试、截图工具和缓存拥有各自的运行目录与保留规则，运行这些工具不触发建单。工具目录的删除由其拥有者负责。
- 临时目录与工单都不提交。值得长期保留的探针成为规范或场景；行为变更写进 `docs/changes/`，方向变更写进架构决策。持久文档不引用临时目录或工单的实例标识。

## 后果

- 日常修改能够直接完成，临时产物在没有工单时也有创建、定位、关闭和回收入口。
- 建单由执行任务的代理按上下文需要判断，命令行工具负责执行明确的建单指令。工具无法从文件改动推断是否需要交接。
- 临时目录的进程存活检查采用保守判断：仍然存活的拥有者会延长保留时间，显式关闭用于结束已经确认完成的会话目录。
- 工单资料随任务保留，运行资料随进程和保留期限退役，两者的清理规则各自明确。

## 重审条件

- 宿主能够提供可靠的会话结束通知或跨机器任务存储时，重新考虑临时目录的拥有者记录与工单的存放位置。
