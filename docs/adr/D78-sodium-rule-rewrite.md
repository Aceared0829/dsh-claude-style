# D78. 改写宿主与插件的昂贵样式规则

## 背景

宿主的对话流样式里有几条规则用 `:has()` 判断一个流条目是否为空，再经兄弟组合子与 `:nth-last-child(… of …)` 把这一判断传给其后的条目；这几条规则的最后一段是「一个不隐藏、也不为空的条目」，页面上几乎每个元素都满足它。浏览器从最后一段开始匹配，于是每次插入都要拿整页去试这几条规则，长会话里样式重算的单价随之上涨，皮肤与宿主在同一帧里任何一次读布局都要付这笔钱。宿主没有为这类规则提供开关。D9 已经要求皮肤自己的结构判断由脚本写成属性、样式只读属性，同样的办法可以用在别人的规则上。

## 决定

- 皮肤提供一个实验性的改写，名为钠：开关打开时，适配表里登记的规则在原样式表里就地改写选择器，把昂贵的结构判断换成皮肤脚本维护的属性；关闭时选择器原样写回、属性全部撤下，页面回到宿主自己的样子。
- 适配表按成员组织。宿主本体的界面由内置插件提供、随宿主一同发版，它与其他插件同等地作为一个成员：每个成员写明自己的版本从哪里读、从哪一版开始适配（更高的版本自动包含）以及它的适配项；每个适配项写明样式表（加载器标在样式节点上的包名与路径）、它认得的规则，以及维护替换属性的脚本。版本读不到的成员不参与改写。
- 表里写的是整条选择器：浏览器序列化出来的样子，带哈希的类名按角色占位，第一次出现时捕获，之后必须是同一个类名。差一个字就匹配不上，规则保持原样；宿主改了规则，页面上留下的就是宿主自己的规则。
- 改写有两种手段：判断交给属性，昂贵的结构判断由脚本按浏览器自己的答案写成属性；收窄最后一段，在几乎匹配一切的那一段里加一个只出现在相关元素上的标记，浏览器只拿这些元素去试。
- 替换与原规则等价：对同一棵树命中同一组元素，优先级相同。标记只加在原规则本来就只可能命中的元素上。属性在宿主改动节点之后、浏览器计算样式之前写入（变化观察的回调里），页面不会有一帧看到两者不一致。
- 开关默认关闭，偏好的初值是「未决定」。读到用户设置之后的探测里，适配表一有规则命中，就替用户打开；用户拨过一次开关，偏好就有了明确的取值，探测不再改它。
- 设置项的小字只报告生效中的规则条数，悬停列出每一条规则的来源与声明，供维护时对照。

## 后果

- 开关打开时，宿主或插件的样式表与它们作者写下的样子不再一一对应；排查样式问题前先关掉开关。
- 适配一条新规则要同时写出它的整条选择器、替换写法与维护属性的脚本，并由规格核对两者在同一棵树上命中同一组元素、在层叠里分量相同；没有维护脚本的规则不进表。
- 宿主每次改动这些规则，表里对应的一条就失效，要按新的写法重新登记。
- 改写作用在样式表对象上，同一份样式被重新注入（热更新）时改写随旧对象一起丢失，皮肤要监视 `<head>` 并对新对象重新匹配。
- 放弃的方案：在皮肤样式表里写更高优先级的规则盖住宿主的声明。盖住之后浏览器照样要求值原规则，开销没有减少。
- 放弃的方案：删除原规则、插入改写后的副本。删除与插入改变规则的下标，关闭时要按记下的位置插回，而宿主自己的增删会让记下的位置失效。

## 重审条件

- 宿主修掉这些规则，或为流条目的空状态提供自己的属性时，对应的适配项删除。
- 浏览器对这类结构选择器的匹配与失效成本降到与普通属性选择器相当时，整个功能删除。
