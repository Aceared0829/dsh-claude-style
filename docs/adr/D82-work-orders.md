# D82. 工单随任务退役

## 背景

D48 把进度与议题留在提交与议题里，但本地仍会长出一层临时文件：测量脚本、DOM 记录、截图、日志各有各的位置，任务结束后没人删，`.debug/` 越积越厚。把测量值写进一份持久文档又会回到 D48 拒绝的做法：同一个数字写在文档、样式、测试与注释里，改一处要同步多处。

任务期间需要的数字与现场证据是真的，任务结束后它们大多不再成立。工单因此按临时容器设计：数字在任务期间有唯一住处，任务结束时要么进入持有它的单一来源，要么随工单消失。

## 决定

- 一个任务一个工单目录 `.debug/work/<id>/`。`work.md` 顶部是 JSON 块，装状态、所有权、验收、测量、验证与交接；正文写背景、范围、取舍与截图说明。`refs/`、`shots/`、`tmp/` 放参考图、证据截图与临时文件。工单不提交。
- `index.json` 由各工单扫描生成，供 `npm run work -- list` 与 Agent Team 查看；不维护第二份手写索引。
- 测量值只写在工单里。进入 review 前，每条测量必须写明退役去处：`token` 进 `tokens.json`，`test` 进 spec，`comment` 进代码注释，`adr` 进方向记录，`none` 表示不持久。没有 `MEASUREMENTS.md` 一类持久测量文档。
- `npm run work -- close` 只在工单处于 review、gate 已通过、每条测量都有去处时删除整个目录。没有归档目录，删除就是退役。
- 工单 id 只出现在工单自己、提交说明和本地索引里。README、ARCHITECTURE、ADR、`docs/changes/` 与 CHANGELOG 不引用工单 id；`work check` 拒绝这种引用。
- 所有临时文件都放进当前工单的 `tmp/`。`npm run work -- gc` 清理没有 `work.md` 的孤儿目录与 `.debug/` 根部的散落临时文件，超过 24 小时的才删。
- 行为变更仍然写 `docs/changes/`，方向变更仍然写 ADR。工单不是它们的替代品。

## 后果

- 工单不进入 git，跨机器的 Agent Team 看不到同一份工单；需要共享时导出一份脱敏快照，或把任务移到外部议题系统。仓库的持久记录仍然是提交、ADR 与变更文件。
- 数字不再有第二份副本。想让一个值活过任务，必须把它放进令牌、测试或注释；否则它随工单消失，这是有意的。
- `.debug/` 的临时文件有了固定去处与删除路径，孤儿目录和散落文件可以由 `work gc` 收走。
- 工单的索引与检查只在本地生效；CI 没有 `.debug/work` 时检查直接通过，云端不依赖工单。

## 重审条件

- 工单需要跨机器共享、审计或由仓库外的人查看时，重新考虑把索引或工单提交进仓库，或改用外部议题系统。
- 工单的生命周期长到超过一个发布周期，退役规则开始妨碍交接时，重审临时容器的定位。
